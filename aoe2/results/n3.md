## G-STEAMAPI, G-MENU — start-up failure found and fixed (finding N3-F1, fixed by Wine patch 0023)

**Symptom.** Launched through Steam (2026-10-07, `steam://rungameid/813780`), AoE2DE exits with code 84 after about
17 s. No window appears, and the menu is never reached. Replaying Steam's launch through MacNeutron's tool, with
Steam's logged environment (`~/aoe2-poc-work/n3/replay-launch.py`), gives the same result every time: exit 84 after
6 s.

**Where it fails.** The game loads normally: `AoE2DE_s.exe` at its base 0x140000000, then `steam_api64.dll`,
`libHttpClient.Win32.dll`, `BugSplat64.dll` and `PartyWin.dll`. It then dies on its main thread with
`wine: Unhandled illegal instruction at address 0000000142B9A04C`.

The bytes at that address on disk are `60 f0 39 65 dc`. `0x60` is invalid in 64-bit mode. They fill exactly the
5-byte slot of a normal prologue (`48 89 5c 24 08`), right before an intact `48 89 7c 24 10 55`.

**Read in the binary.** `AoE2DE_s.exe` carries the string `ARXAN`: Arxan (Digital.ai) anti-tamper, which
PCGamingWiki lists for every edition of the game. Arxan keeps code corrupted until its guards repair it at run time.
After a failed integrity or environment check, it lets execution reach unrepaired code. The SEH trace shows no
exception before the fault except two routine RPC 0x6ba. Thread 0184's NULL reads in `RtlUserThreadStart` come from
the debugger's break-in thread, started after the crash. So the guard that should have repaired this function did not
run, or chose not to repair it. The fault happens at the function's first instruction: FEX does not mistranslate
real code here.

**Ruled out so far** (each replayed; exit 84 at the same address every time):
- Steam's overlay libraries (`DYLD_INSERT_LIBRARIES`): no change without them.
- Wine logging (`WINEDEBUG=-all`): no change without it.
- msync (`MACNEUTRON_NO_MSYNC=1`): no change with it off.
- ntdll looking hooked to x64 code: the x64-visible `NtQueryInformationProcess` is a genuine Windows-style x64
  syscall stub (`4c 8b d1 b8 19 00 00 00 f6 04 25 08 03 fe 7f 01`), not a jump.

**Context.**
- On Linux, Proton 8.0-4 and later runs the game (aoe2.arkanosis.net, updated 2026-01-01), so Arxan accepts Wine
  there.
- Sikarugir issue #233 reports that the game's 2026-06-02 update (177723) stopped it launching on macOS Wine 10 under
  Rosetta. That is a different fault (a NULL read at 0x142CFE67A), and the report has no root cause.
- Next candidates, in order: what CPUID reports under FEX (hypervisor bit, brand and feature bits that disagree with
  each other); debugger checks (debug registers in thread contexts, `ProcessDebugPort` and `ProcessDebugFlags`,
  `NtQueryInformationThread` hide-from-debugger); timing (RDTSC against the wall clock).

**N4 note.** The same Linux guide says online play needs Microsoft's own `ucrtbase.dll` from `vc_redist.x64.exe` in
the prefix: Wine's desyncs after a few seconds.

Evidence: `~/aoe2-poc-work/n3/` (`launch1/` with screenshots, process samples and the Rosetta check; `r1/` and
`e1`–`e3` replays). The game log is `~/Library/Logs/MacNeutron/steam-813780.log`; MacNeutron redacts its account
values, and the replay script also leaves out the login names.

### Root cause and fix

**Root cause** (runtime passed): `+server` showed what the main thread does last before the fault.
1. It asks for the file mapped at its own base address (`get_mapping_filename`, which is
   `NtQueryVirtualMemory(MemoryMappedFilenameInformation)`). Wine answers `\??\Z:\…\AoE2DE_s.exe`.
2. It then tries three times to open `\??\GLOBALROOT\??\Z:\…\AoE2DE_s.exe` (twice) and `…\AoE2DE.dat`, for
   reading. Each open fails with `OBJECT_NAME_NOT_FOUND`, and the fault follows.

That is the anti-tamper check reading its own files. `\??\GLOBALROOT` links to the root of the namespace, so the
name is the file `\??\Z:\…`. But Wine's `get_dos_prefix_len()` (in `dlls/ntdll/unix/file.c`) recognised only `\??\`
and `\DosDevices\`. The name therefore went to the server as an object path and was not found.

**How it was narrowed down:**
- Dumping `.text` from the crashed process with `lldb` showed it byte-identical to the file: Arxan had decrypted
  nothing.
- The crashing function has one direct caller, an ordinary run-once initialiser. The entry point and TLS callbacks are
  standard MSVC code.
- A probe of what x64 code sees under FEX (`wine-arm64/tests/x64-envprobe.c`) showed four differences from a real
  Intel PC: hypervisor bit set (`FEXIFEXIEMU`), an `Apple Silicon` brand string with an Intel family/model, RDTSC that
  can repeat, and the `int 2d` addresses. None of the first three changes the crash (`FEX_HIDEHYPERVISORBIT=1`,
  `FEX_SMALLTSCSCALE=0`); `int 2d` was not tested against the game. The debugger checks all look like Windows without
  a debugger.
- The x64-visible ntdll and kernelbase exports are Microsoft-format thunks (`48 8b c4 48 89 58 20 55 5d e9`), and
  kernel32's forwarders are `ff 25` stubs, as on x64 Windows.

**Reproducer:** `wine-arm64/tests/arm64-globalroot.c`, built for ARM64 and for x64. It opens its own executable
through `\\?\GLOBALROOT` plus its mapped name, and `win.ini` through `\??\` and `\DosDevices\`. All three opens
failed with error 2 in both lanes, so this is not specific to FEX. The controls passed: the plain path and
`\\?\GLOBALROOT\Device\Null`.

**Fix:** Wine patch 0023 skips any leading `\??\GLOBALROOT` before checking the DOS prefixes. The reproducer then
passes in both lanes. Gate: `check.sh globalroot` (PASS).

**Result:** replayed through a tool folder built from the patched runtime, the game runs. After 100 s it was still
running, at about 2.3 GB and nearly three CPU cores, with the Steam API's callbacks active. A `winshot` capture of its
window (`~/aoe2-poc-work/n3/g1-globalroot/game.png`) shows the **main menu**: version 101.103.54800.0 (#185872),
build 25464371, the Steam persona, "Not signed into Xbox Network", and a dialog saying the free "Enhanced Graphics
Pack" DLC is not installed. Menu text renders correctly.

### Finding N3-F4: the hang reporter deadlocks in Wine's futex queue (fixed by Wine patch 0024)

**Symptom:** splash screen or black window, then either a frozen process or an exit with code 0 about 3 minutes after
launch; Steam shows Play again.

**Evidence** (temporary Wine instrumentation, saved as `$AOE2_WORK_ROOT/diag-wine-20261007.patch`, not part of the
series): the main thread creates a watchdog (start `0x142C37F58`, parameter `0x2710`) and a reporter (start
`0x142C18ED4`). When start-up has stalled for about two minutes, the reporter terminates the watchdog (FEX's
`ThreadTerm` suspends it first), pre-sizes a file (`FileAllocationInformation`), suspends every other thread, and then:
- `arm64ec exception c0000005 pc 6fffffa414a4 (read 0x7a5fb00) holding futex queue 99`: `RtlWakeAddressAll()` read a
  futex entry in freed memory, the terminated thread's emulator stack, which `ThreadTerm` had freed;
- the access violation went to FEX's `ResetToConsistentState`, which takes `ThreadCreationMutex`; the mutex's release
  woke waiters through the same queue, and the thread spun on its own spinlock for good.

**Reproducer and fix:** `wine-arm64/tests/arm64ec-futexterm.c` (check step `futexterm`) fails in both lanes before the
patch (a lost wakeup, then the page fault in `RtlWakeAddressAll` at the instruction the game faulted at) and passes
after it. Patch 0024 makes the ARM64EC `NtTerminateThread()` stop the thread and unlink its futex entries before
`ThreadTerm` runs.

N3-F2 (exit 2, "nested exception on signal stack") was not seen as such. The same message appeared when `lldb` attached
to the frozen game; whether N3-F2 is this reporter path is not confirmed.

**Still open (N3-F5):** the reporter can still deadlock on another path. In one run (22:21) it again left 57 threads
suspended and one thread spinning in `RtlWakeAddressAll()`. It only matters when the reporter fires, which N3-F6 causes.

## 2026-10-08: N3-F5, N3-F6 and G-TEXT causes found (runtime with Wine 0025–0026, DXMT 0003, FEX 0006–0009)

### N3-F5 fixed (Wine patch 0025)

RtlWaitOnAddress waits now sleep in the kernel's address queues (os_sync_wait_on_address); no user-mode spinlock or
queue entry is left for a suspended thread to hold. Mods-on runs no longer freeze in the reporter. Check steps
`waitaddr` and `suspendwake`.

### N3-F6: the mods stall was Arxan's self-modifying code under FEX (FEX patches 0006–0009)

Not network, not disk, not Steam: during the stall the game uses ~1.5 cores. While mods load, the game's anti-tamper
code runs ~15,000 illegal-instruction traps a second (one per protected instruction, about 2 million in all) and patches
the game's own instructions ~19,000 times a second over ~4,300 pages of `.text`. Each patch faulted on an RWX page FEX
had write-protected because it held compiled code: invalidate the page's code in every thread (decommitting each
thread's 4 MB call-ret stack), unprotect, and protect again at the next compile. Three threads did this at once and
spent most of the time waiting on each other's locks in FEX and Wine.

| Runtime | Mods load (setup communications handler → modded languages) | Menu |
| --- | --- | --- |
| before 0006 | 95–130 s | ~110–150 s, then the game usually died |
| 0006 (256 KB call-ret stack) | ~92–97 s | ~107 s |
| 0009 prototype (check per instruction) | ~29 s | +41 s |
| 0009 (check per block) | ~24 s | +35 s |

Patch 0009 leaves a page writable after 16 write faults on compiled code; blocks from it check their bytes once on
entry (tight loop 1.08x, against 1.47x for FEX's per-instruction check). `MACNEUTRON_SMC_SELFCHECK=0` turns it off.
Test programs: `x64-arxantrap` (µs per trap: 26 → 15 → 4.8 for the write-fault pattern) and `x64-smcspeed`. The FEX
patches are downstream only: FEX does not accept AI-generated contributions.

Wine patch 0026 (a far-off relative timeout expired at once, so ntdll's threadpool timer thread spun) was found on the
way; it was a real busy loop but not this stall. A 15 s start at 03:39 was a post-crash start that skipped the mods.

Diagnostics that work here: FEX `ProfileStats` (patch 0008; `{"Config":{"ProfileStats":"1"}}` in
`~/.config/fex-emu/AppConfig/AoE2DE_s.exe.json`, read with `$AOE2_WORK_ROOT/tools/fexstats.c`; the counter is 1 GHz on
M4), `sample`, and FEX's debug log (`"SilentLog":"0"`; one line per handled SMC fault).

### G-TEXT: cause found and fixed (DXMT patch 0003), not yet confirmed in game

The menu text vertex shader packs TEXCOORD0/1 into o1.xy/o1.zw; the gradient text pixel shader reads v1.xyzw. airconv
linked varyings by register and first component, so v1.zw (the glyph atlas coordinate) read zeros.
`arm64ec-d3d11packed` reproduces it and passes with the patch.

Logs and captures: `$AOE2_WORK_ROOT/runs/n3-20261008/`.

### N3-F7: with any mod the game stopped behind a black window (fixed by FEX patch 0010)

Bisection (`$AOE2_WORK_ROOT/tools/modtry.sh`): no mods, menu at +18 s; any single mod, even a small one, no menu. The
game sat idle (~18% CPU) and ignored Enter and Escape. Wine's log showed a new thread waiting on a critical section in
FEX's data (`ThreadCreationMutex`), owned by a game thread whose last message was
`wincodecs:BitmapScaler_Initialize` (mod thumbnails).

`winedbg` cannot attach then (its break-in thread blocks in FEX's `ThreadInit`), and `GetThreadContext` on a thread
inside FEX never returns: ARM64EC suspends such a thread only cooperatively. `$AOE2_WORK_ROOT/tools/stackscan.c` reads
a thread's state without suspending it: Wine's syscall frame (TEB+0x378), the ARM64EC CPU area and the stack. The owner
waited on FEX's `CodeInvalidationMutex` (state word `0xc0010000`: write-owned, one writer waiting) and held it itself:

a self-checked block (patch 0009) whose bytes changed → `ThreadRemoveCodeEntry` → `InvalidateGuestCodeRange` with
callbacks enabled → `InvalidateIntervalInternal` (takes the mutex) → `VirtualDontNeed` of the call-ret stack (a
decommit) → Wine's ARM64EC `NtFreeVirtualMemory` notifies FEX → `NotifyMemoryFree` → `InvalidateIntervalInternal` →
waits forever.

Patch 0010 disables the callbacks for that call and takes `ThreadCreationMutex`, as FEX's other invalidations do.
`x64-smcspeed` now also rewrites code without `FlushInstructionCache`, as x86 allows: it hung before the patch and passes
after. Its earlier rewrite case flushed, so it never reached this path.

The morning's "dies 1–3 minutes after the menu" runs (a new thread holding the loader lock forever) were most likely the
same deadlock: a new thread waiting in FEX's `ThreadInit` while it holds the loader lock. Not seen since patch 0010.

### Wine patch 0027: thread stacks no longer probe a 385 GB guard region

`try_map_free_area()` tried every 64 KB step of a range Wine's views leave free. macOS maps memory Wine does not track,
among it a 385 GB guard region (`0xfc0000000`–`0x7000000000`) in the game's process, so each thread stack, placed
bottom-up from 4 GB, failed through it one `mmap` at a time: the game's 175 free-area searches took 13.9 s. On `EEXIST`
the search now asks `mach_vm_region()` for the mapping in the way and continues past it: 195 searches, 22 ms.

### With mods, after patch 0010: a long anti-tamper phase

- The game no longer freezes. After setup its main thread runs Arxan code from a dynamically allocated executable
  region; across threads FEX compiles ~57,000 blocks a second (FEX stats), one thread is always in the
  `NtContinue`-to-emulation path (`raise(SIGUSR2)`), and the menu does not appear. One small mod (3080) is enough.
- About 3.5 min after launch the hang reporter ends the game (exit 0; it pre-sizes a file, `NtSetInformationFile`
  class 19). With both reporter threads (start `0x142C18ED4`) suspended, the game still ended 282 s after setup, with
  exit 1, cause not found.
- Not known yet: whether the phase ends at all under FEX, and how long it needs. On Linux (native x86) it is not
  noticeable.
