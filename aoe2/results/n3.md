## G-STEAMAPI, G-MENU — start-up failure found and fixed (finding N3-F1, fixed by Wine patch 0023)

**Symptom.** Launched through Steam (2026-10-07, `steam://rungameid/813780`), AoE2DE exits with code 84 after about
17 s. No window appears, and the menu is never reached. Replaying Steam's launch through MacNeutron's tool, with
Steam's logged environment (`~/aoe2-poc-work/n3/replay-launch.py`), gives the same result every time: exit 84 after
6 s.

**Where it fails.** The game loads normally: `AoE2DE_s.exe` at its base 0x140000000, then `steam_api64.dll`,
`libHttpClient.Win32.dll`, `BugSplat64.dll` and `PartyWin.dll`. It then dies on its main thread with
`wine: Unhandled illegal instruction at address 0000000142B9A04C`.

The bytes at that address on disk are `60 f0 39 65 dc`. `0x60` is invalid in 64-bit mode. They fill exactly the
5-byte slot of a normal prologue (`48 89 5c 24 08`), right before an intact `48 89 7c 24 10 55`.

**Read in the binary.** `AoE2DE_s.exe` carries the string `ARXAN`: Arxan (Digital.ai) anti-tamper, which
PCGamingWiki lists for every edition of the game. Arxan keeps code corrupted until its guards repair it at run time.
After a failed integrity or environment check, it lets execution reach unrepaired code. The SEH trace shows no
exception before the fault except two routine RPC 0x6ba. Thread 0184's NULL reads in `RtlUserThreadStart` come from
the debugger's break-in thread, started after the crash. So the guard that should have repaired this function did not
run, or chose not to repair it. The fault happens at the function's first instruction: FEX does not mistranslate
real code here.

**Ruled out so far** (each replayed; exit 84 at the same address every time):
- Steam's overlay libraries (`DYLD_INSERT_LIBRARIES`): no change without them.
- Wine logging (`WINEDEBUG=-all`): no change without it.
- msync (`MACNEUTRON_NO_MSYNC=1`): no change with it off.
- ntdll looking hooked to x64 code: the x64-visible `NtQueryInformationProcess` is a genuine Windows-style x64
  syscall stub (`4c 8b d1 b8 19 00 00 00 f6 04 25 08 03 fe 7f 01`), not a jump.

**Context.**
- On Linux, Proton 8.0-4 and later runs the game (aoe2.arkanosis.net, updated 2026-01-01), so Arxan accepts Wine
  there.
- Sikarugir issue #233 reports that the game's 2026-06-02 update (177723) stopped it launching on macOS Wine 10 under
  Rosetta. That is a different fault (a NULL read at 0x142CFE67A), and the report has no root cause.
- Next candidates, in order: what CPUID reports under FEX (hypervisor bit, brand and feature bits that disagree with
  each other); debugger checks (debug registers in thread contexts, `ProcessDebugPort` and `ProcessDebugFlags`,
  `NtQueryInformationThread` hide-from-debugger); timing (RDTSC against the wall clock).

**N4 note.** The same Linux guide says online play needs Microsoft's own `ucrtbase.dll` from `vc_redist.x64.exe` in
the prefix: Wine's desyncs after a few seconds.

Evidence: `~/aoe2-poc-work/n3/` (`launch1/` with screenshots, process samples and the Rosetta check; `r1/` and
`e1`–`e3` replays). The game log is `~/Library/Logs/MacNeutron/steam-813780.log`; MacNeutron redacts its account
values, and the replay script also leaves out the login names.

### Root cause and fix

**Root cause** (runtime passed): `+server` showed what the main thread does last before the fault.
1. It asks for the file mapped at its own base address (`get_mapping_filename`, which is
   `NtQueryVirtualMemory(MemoryMappedFilenameInformation)`). Wine answers `\??\Z:\…\AoE2DE_s.exe`.
2. It then tries three times to open `\??\GLOBALROOT\??\Z:\…\AoE2DE_s.exe` (twice) and `…\AoE2DE.dat`, for
   reading. Each open fails with `OBJECT_NAME_NOT_FOUND`, and the fault follows.

That is the anti-tamper check reading its own files. `\??\GLOBALROOT` links to the root of the namespace, so the
name is the file `\??\Z:\…`. But Wine's `get_dos_prefix_len()` (in `dlls/ntdll/unix/file.c`) recognised only `\??\`
and `\DosDevices\`. The name therefore went to the server as an object path and was not found.

**How it was narrowed down:**
- Dumping `.text` from the crashed process with `lldb` showed it byte-identical to the file: Arxan had decrypted
  nothing.
- The crashing function has one direct caller, an ordinary run-once initialiser. The entry point and TLS callbacks are
  standard MSVC code.
- A probe of what x64 code sees under FEX (`wine-arm64/tests/x64-envprobe.c`) showed four differences from a real
  Intel PC: hypervisor bit set (`FEXIFEXIEMU`), an `Apple Silicon` brand string with an Intel family/model, RDTSC that
  can repeat, and the `int 2d` addresses. None of the first three changes the crash (`FEX_HIDEHYPERVISORBIT=1`,
  `FEX_SMALLTSCSCALE=0`); `int 2d` was not tested against the game. The debugger checks all look like Windows without
  a debugger.
- The x64-visible ntdll and kernelbase exports are Microsoft-format thunks (`48 8b c4 48 89 58 20 55 5d e9`), and
  kernel32's forwarders are `ff 25` stubs, as on x64 Windows.

**Reproducer:** `wine-arm64/tests/arm64-globalroot.c`, built for ARM64 and for x64. It opens its own executable
through `\\?\GLOBALROOT` plus its mapped name, and `win.ini` through `\??\` and `\DosDevices\`. All three opens
failed with error 2 in both lanes, so this is not specific to FEX. The controls passed: the plain path and
`\\?\GLOBALROOT\Device\Null`.

**Fix:** Wine patch 0023 skips any leading `\??\GLOBALROOT` before checking the DOS prefixes. The reproducer then
passes in both lanes. Gate: `check.sh globalroot` (PASS).

**Result:** replayed through a tool folder built from the patched runtime, the game runs. After 100 s it was still
running, at about 2.3 GB and nearly three CPU cores, with the Steam API's callbacks active. A `winshot` capture of its
window (`~/aoe2-poc-work/n3/g1-globalroot/game.png`) shows the **main menu**: version 101.103.54800.0 (#185872),
build 25464371, the Steam persona, "Not signed into Xbox Network", and a dialog saying the free "Enhanced Graphics
Pack" DLC is not installed. Menu text renders correctly.

## Rebuilt app, launched from Steam (2026-10-07 09:22Z, runtime `ec23d32`)

- **Launch through Steam works.** The game, with Steam's argument `SKIPINTRO`, gets past the GLOBALROOT check and
  shows its splash screen (1280×960 window, `winshot` capture `n3/launch2/game.png`). It creates a D3D11 device at
  feature level 11_0.
- **Crash (finding N3-F2, open):** about 80 s after launch, near the menu, the game dies with exit 2. The game log's
  last error: `00f8:err:virtual:virtual_setup_exception nested exception on signal stack addr 0x19cc4c10c`, which is
  `_sigtramp` itself, on the main thread.
- **Exception storm (finding N3-F3, open):** a replay of the same launch with `+seh` (`n3/r4-skipintro/`) counted
  about 720,000 `STATUS_ILLEGAL_INSTRUCTION` exceptions in about 80 s. They come from eight fixed addresses in
  `AoE2DE_s.exe`: four near `0x140F77B90`–`0x140F77E3C` (about 122,000 each) and four at `0x142D22BE1`–`0x142D22BE9`
  (about 59,000 each). The bytes there are deliberately invalid in 64-bit mode (`0xEA`, `0x16`, `0x06`), and some are
  decrypted at run time. This is Arxan's exception-driven control flow, caught by its vectored handler. On this
  runtime each exception is a host signal plus Wine and FEX dispatch.
  - Working hypothesis, not yet tested: this load starves the main thread, which would explain the user's report of
    unresponsive clicks and garbled frames, and stresses the signal path enough to produce N3-F2.
- That traced replay filled the disk with its 1.1 GB log and stalled before the crash. Evidence of the counts:
  `n3/r4-skipintro/exceptions.txt`.

Disk: 6.8 GB free after removing regenerable build scratch and two superseded app backups. AoE2DE takes 24 GB, and the
main and clean checkouts take 14 GB each.
