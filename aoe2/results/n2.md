## Findings

### F1 — fixed: write-watched RWX memory spun forever on ARM64 (Wine patch 0021)

- Found by A64-EXEC-ROLLBACK, which timed out at 30 s.
- Reduced to `wine-arm64/tests/arm64-wxwatch.c`: a `MEM_WRITE_WATCH` `PAGE_EXECUTE_READWRITE` page, rewritten and
  run. It hung after run 1, at 100% CPU, in `_sigtramp`.
- Cause (*read in source*, then confirmed by the fix): after patch 0006 flips a page to read-exec, Wine's record
  still says writable. `virtual_handle_fault`'s "ignore fault if page is writable now" check then succeeds for a
  write-watch range, without changing the host protection. The flip back to read-write never runs, and the store
  faults again forever.
- Fix: skip that check for W^X-degraded pages and let the flip handle them.
- After the fix, `arm64-wxwatch` passes with 10 flips to rx and 13 to rw, and exec-rollback passes. Gate:
  `check.sh wxwatch`.
- Who it affects: native ARM64 processes that combine write-watch with JIT code (a GC with a JIT). FEX's dual-view
  JIT never flips, which is why the x64 lane passed.

### F2 — fixed: system APCs killed an ARM64EC process while it started (Wine patch 0022)

- Found by winetest kernel32 `sync` under FEX: 34,270 failures, against 2 natively. Its `test_apc_deadlock` child
  died at start, and every later remote call failed with `STATUS_PROCESS_IS_TERMINATING`.
- Reduced to `wine-arm64/tests/x64-apcsuspend.c alloc`: remote `NtAllocateVirtualMemory`/`NtFreeVirtualMemory`
  into an x64 child as it starts. The child died in 3 of 3 runs (exit 1, `nested exception on signal stack` in
  `_platform_memmove`). The ARM64 control lived. Suspends alone, and allocations made while the thread was
  suspended, did not kill it.
- Cause, from temporary instrumentation in `usr1_handler` (since removed): the signal arrives while an ARM64EC process
  loads FEX's unix library. The call chain is `__wine_syscall_dispatcher` → `NtQueryVirtualMemory` →
  `load_unixlib_by_name` → dyld `dlopen` → `__mmap`.
- macOS's dyld runs `dlopen` on a stack of its own, outside Wine's kernel stack. So `is_inside_syscall()` said "PE
  code", and the handler saved and restored host state as a user-mode context.
- Fix: `x18_call` records whether the custom x18 ABI was on at the signal, which is true in PE code only. SIGUSR1,
  SIGUSR2 and SIGQUIT count a signal as inside the syscall when the ABI was off and the stack is neither the kernel
  stack nor the PE stack. Everywhere else the existing test is unchanged.
- After the fix: `x64-apcsuspend` lives in 5 of 5 runs (about 3,600 remote alloc/free pairs each). kernel32 `sync`
  under FEX drops from 34,270 failures to 2, the native count. ntdll `virtual` under FEX drops from 8 to 0. No
  native unit regressed. Gate: `check.sh apcsuspend`.
- Why it matters for AoE2: anything that writes into a starting x64 game process (Steam's overlay injection, crash
  reporters, debuggers) would have hit this.

### F3 — *read in source*: hardware TSO is never used on macOS (performance item for N3)

- FEX's macOS unixlib answers `SetHardwareTSOControl(Enable)` with `STATUS_NOT_SUPPORTED`. So `TSOHandlerConfig`
  never calls `SetHardwareTSOSupport(true)`, and FEX emits software TSO (ordered loads and stores) for all
  translated code.
- Correctness holds: G2's litmus forbids every reordering with TSO on. With TSO off, MP shows 964,493 per 10 M.
  Native ARM64 code never runs with TSO.
- P0 shows that `thread_set_x86_64_compat` works here, on the main thread and on fresh threads. Per-thread hardware
  TSO in FEX's macOS unixlib (enabled on each thread that runs translated code) is a candidate for N3's G-PERF.
- It is not done here: it needs a per-thread hook, a G2 rerun and a measured gain.

### F4 — ruled out (test fixture): the fixed executable-memory addresses collide under FEX

The companion's fixed addresses 0x60000000 and 0x61000000 lie inside a committed read-exec region from 0x3ffe0000 in
an x86-64 process under FEX. That made X64-EXEC-RWX, X64-EXEC-TRANSITION and X64-EXEC-ALLOC-STATE fail with error
487. These cases now take the first free 64 KiB slot above those addresses, found with `VirtualQuery`. Every assertion
is unchanged, and all three pass.

### F5 — ruled out (Wine ARM64EC conformance, not this platform): ntdll `rtl` crashes under FEX

`test_RtlDestroyHeap` with `BeingDebugged` makes `RtlDestroyHeap` call `DbgBreakPoint`. In an ARM64EC process that
is ntdll's native ARM64 code. The test's x64 handler skips the breakpoint with `Rip += 1`, which lands mid-instruction
(an execute fault at `0x6fffffa3cca5`, `info[0]=8`), and the process dies. Only code that steps over a breakpoint
inside ntdll by hand is affected. Not pursued for AoE2.
